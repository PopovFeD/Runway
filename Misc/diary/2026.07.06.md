# Runway — журнал разработки

## Дата

06.07.2026

## Цель этапа

Определить общую архитектуру проекта, выбрать способ разработки без доступа к реальному микроконтроллеру и реализовать минимальный эмулятор устройства для проверки обмена данными по последовательному порту.

---

# Исходная задача

Проект представляет собой настольное приложение для взаимодействия с микроконтроллером, подключённым по USB (виртуальный COM-порт). Предполагается работа с датчиками температуры и влажности, а в дальнейшем — возможность подключения дополнительных датчиков и исполнительных устройств.

Функции настольного приложения:

* подключение к устройству;
* получение данных;
* отображение данных в графическом интерфейсе;
* сохранение измерений;
* экспорт результатов;
* передача управляющих команд на микроконтроллер.

В качестве технологии интерфейса выбран Avalonia UI, язык разработки — C#.

---

# Обсуждение архитектуры

Первоначально рассматривалась идея сразу начать разработку графического интерфейса. После обсуждения было принято решение сначала построить ядро приложения, а затем подключить GUI.

Предлагаемая последовательность разработки:

1. эмулятор микроконтроллера;
2. транспортный уровень (COM);
3. получение кадров из потока байтов;
4. разбор протокола;
5. хранение данных;
6. графический интерфейс.

Такой порядок позволяет тестировать каждый слой независимо и не связывать разработку интерфейса с готовностью аппаратной части. Кроме того, модульная архитектура упрощает отладку: каждый компонент можно проверять отдельно, не пытаясь сразу искать ошибку во всей системе целиком. Это особенно важно на раннем этапе, когда ещё нет реального устройства и нужно убедиться, что корректно работают и обмен данными, и протокол, и последующая обработка.

Также модульность оставляет возможность в будущем заменить или расширить транспортный уровень. Сейчас основной вариант связи — последовательный порт по USB, но в перспективе возможно подключение по Ethernet. Если архитектура будет разделена на независимые слои, переход на другой канал связи не потребует полной переработки приложения, а затронет только соответствующий модуль.

---

# Выбор способа эмуляции

Поскольку доступ к реальному микроконтроллеру отсутствует, принято решение написать отдельную программу-эмулятор на Python.

Для обмена данными используются виртуальные COM-порты, созданные при помощи com0com.

После настройки была получена рабочая схема:

Python → COM4

COM4 ↔ COM6

C# → COM6

Проверка выполнялась передачей случайных байтов. После настройки виртуальных портов обмен был успешно установлен.

---

# Разработка эмулятора

Минимальный пример был постепенно переработан.

В текущей версии:

* используется argparse;
* номер COM-порта задаётся из командной строки;
* скорость соединения также задаётся параметром;
* реализована модель датчиков температуры и влажности;
* значения изменяются плавно при помощи небольших случайных отклонений;
* данные сериализуются и отправляются по COM.

Использование argparse решено сохранить, поскольку номер порта зависит от конкретного компьютера и оборудования.

---

# Проектирование протокола

После обсуждения было принято решение отказаться от передачи текстовых строк.

Выбран бинарный протокол.

Структура пакета:

* сигнатура (Magic);
* версия протокола;
* тип сообщения;
* порядковый номер пакета (Sequence);
* длина полезной нагрузки;
* полезная нагрузка;
* контрольная сумма CRC-16.

Даже несмотря на учебный характер проекта, использование CRC-16 признано оправданным. Проверено, что алгоритм без проблем помещается в память Arduino Nano и широко применяется в промышленных последовательных протоколах.

В качестве полезной нагрузки пока используются значения температуры и влажности.

Передача выполняется не в формате float, а как целые числа в сотых долях единицы измерения (например, 24.53 °C передаётся как 2453). Такой подход соответствует типичной практике разработки встроенных систем и избавляет от особенностей представления чисел с плавающей точкой на различных платформах.

---

# Зарезервированные типы сообщений

Для дальнейшего расширения протокола зарезервированы типы сообщений:

* SensorData;
* Command;
* Ack;
* Error;
* Ping;
* Pong.

На текущем этапе используется только SensorData.

---

# Хранение данных

Предварительно принято решение использовать SQLite.

Причины выбора:

* отсутствие отдельного сервера;
* достаточная производительность;
* удобство резервного копирования;
* простая интеграция с C#.

Отдельно обсуждалось, что запись должна быть отделена от получения данных. В дальнейшем между транспортом и базой данных предполагается использовать очередь сообщений или аналогичный механизм, чтобы запись не блокировала получение пакетов.

---

# Следующий этап

Следующей задачей определено создание модуля чтения последовательного порта.

При этом важно разделить две различные задачи:

1. выделение отдельных пакетов из непрерывного потока байтов (Frame Reader);
2. разбор содержимого уже полученного пакета (Packet Parser).

На данном этапе решено сначала реализовать именно выделение кадров, а уже затем переходить к полноценному разбору протокола.

# Решения, принятые по итогам этапа

* основной язык настольного приложения — C#;
* GUI реализуется на Avalonia UI;
* микроконтроллер временно заменяется Python-эмулятором;
* обмен выполняется через виртуальные COM-порты;
* выбран бинарный протокол передачи данных;
* предусмотрена возможность дальнейшего расширения протокола;
* для контроля ошибок используется CRC-16;
* значения датчиков передаются в виде целых чисел с фиксированной точкой;
* предполагаемое хранилище данных — SQLite;
* архитектура строится модульно, чтобы упростить отладку и последующее развитие системы;
* в будущем возможно подключение не только по COM, но и по Ethernet;
* разработка будет вестись от ядра системы к пользовательскому интерфейсу, а не наоборот.
