# Что сделано

## 1. Channel<Frame> — разделение read-потока и обработки

`OnDataReceived` (вызывается прямо из read-потока `SerialTransport`) теперь
только режет байты на кадры (`FrameReader.Append`) и кладёт их в
`Channel<Frame>` (безлимитный, `SingleReader`/`SingleWriter`). Разбор пакета
(`PacketParser.Parse`) и всё, что с ним связано, переехали в отдельную
задачу `ProcessFramesAsync` — сюда же в будущем ляжет запись в SQLite,
не задевая read-поток порта.

## 2. Ограничение логов + файловый лог

`LogEntries` в GUI рос всю сессию без остановки — типичная медленная утечка
памяти. Решение: два разных потока логов вместо одного.

* `BoundedLog` (`Core/Logging/BoundedLog.cs`) — обёртка над
  `ObservableCollection<string>` с жёстким капом (`AppSettings.MaxLogEntries`,
  по умолчанию 500). При превышении вытесняет самые старые записи.
  Вынесена отдельным классом специально ради тестируемости без
  Avalonia-контекста.
* `LogFileWriter` (`Core/Logging/LogFileWriter.cs`) — пишет **все** строки
  без ограничения в `runway.log` (`AppSettings.LogFilePath`). SQLite ради
  этого заводить пока рано — обычный append-only файл почти ничего не
  стоит по памяти, а слой хранения всё равно не за горами.
* `IUiDispatcher`/`AvaloniaUiDispatcher` (`Core/Threading/`) — абстракция
  над `Dispatcher.UIThread.Post`, без неё юнит-тесты на весь пайплайн
  (`Channel<Frame>` → парсинг → лог) были бы невозможны без тяжёлого
  `Avalonia.Headless`.

Найденный по ходу баг: `{t.Temperature:F2}` без явной культуры даёт `24,53`
вместо `24.53` на системах с русской локалью (обнаружил не я, а прогон
`dotnet test` на реальной машине — до этого не было теста, проверяющего
точный формат строки). Поправлено через `CultureInfo.InvariantCulture` —
и в форматировании телеметрии, и в таймстампах обоих логов (`:` в custom
date/time формате — тоже не литерал, а `TimeSeparator` текущей культуры).

## 3. Microsoft.Extensions.Logging для diagnostics

Обсудили: свой `LogFileWriter` — это узкий сериализатор данных телеметрии,
не логгер общего назначения (нет уровней, категорий, ротации). Полноценный
Serilog/NLog ради него — оверинжиниринг, он всё равно временный (TODO).
Но для событий уровня приложения (разрыв порта, попытки переподключения)
уровни и категории — это ровно то, для чего логгеры существуют. Выбор —
`Microsoft.Extensions.Logging`: первый пакет, минимальный порог входа,
без ротации (сознательно, не нужна пока).

* `FileLoggerProvider`/`FileLogger` (`Core/Logging/FileLoggerProvider.cs`) —
  минимальный `ILoggerProvider`/`ILogger` без сторонних пакетов, пишет в
  отдельный `runway.diagnostics.log` (`AppSettings.DiagnosticsLogFilePath`).
  Отдельно от `runway.log` намеренно — данные телеметрии и диагностика
  приложения не должны мешаться в одном потоке строк.
* `AppendOnlyFile` (`Core/Logging/AppendOnlyFile.cs`) — общая обёртка над
  `StreamWriter`, вынесена из `LogFileWriter`, чтобы не дублировать её же
  в `FileLoggerProvider`.
* В `App.axaml.cs` — `LoggerFactory` с `AddConsole()` (видно при разработке)
  и `AddProvider(fileLoggerProvider)`. Поймал у себя баг при вычитке:
  `using var loggerFactory` продиспозил бы фабрику (а с ней и
  `fileLoggerProvider` — `LoggerFactory` владеет переданными провайдерами)
  сразу по выходу из `OnFrameworkInitializationCompleted`, то есть
  практически сразу после старта, а не при выходе из приложения. Убрал
  `using`, диспозю вручную в `desktop.Exit`.

## 4. Переподключение при разрыве порта

`SerialTransport` переписан на цикл `RunLoop`: открыть порт → читать
(`ReadLoop`) пока получается → при разрыве закрыть и подождать
(`WaitBeforeRetry`, шагами по 100мс — чтобы `Close()` не залипал на всю
паузу) → открыть заново. Крутится, пока не позовут `Close()`.

* Новое событие `ISerialTransport.ConnectionStateChanged`
  (`Connected`/`Disconnected`/`Reconnecting`) — проброшено в
  `MainWindowViewModel.ConnectionStatus` и забиндено в `MainWindow.axaml`
  простым `TextBlock`.
* Логирование через `ILogger<SerialTransport>`: Info на успешное открытие,
  Warning на разрыв, Error на неудачную попытку открыть порт (с самим
  исключением).
* Побочный эффект изменения поведения: раньше неверное имя порта в
  `settings.json` роняло `Open()` с необработанным исключением прямо на
  старте приложения. Теперь `TryOpenPort` ловит исключение, логирует и
  просто уходит в `WaitBeforeRetry` — то есть неправильный порт теперь
  тихо (но с логом) ретраится вместо явного краша на старте. Стоит иметь
  в виду при отладке настроек порта — если что-то не подключается, смотреть
  в `runway.diagnostics.log`, а не ждать исключения в консоли.

---

# Почему именно так

* Два отдельных файла лога (`runway.log` для данных, `runway.diagnostics.log`
  для событий) — не техническая прихоть, а прямое следствие разговора
  про природу логгера: смешивать поток телеметрии с событиями вроде
  "порт разорван, попытка 3" сделало бы неудобным чтение обоих.
* `WaitBeforeRetry` спит шагами по 100мс, а не одним
  `Thread.Sleep(_reconnectDelay)` — иначе `Close()` при выходе из
  приложения ждал бы до конца полной паузы переподключения.

# Не сделано / оставлено как есть

* Сам цикл переподключения (`TryOpenPort`/`WaitBeforeRetry` с реальным
  `SerialPort`) не покрыт автотестами. С `com0com` физический разрыв не
  смоделировать — виртуальная пара портов не "отваливается", даже если
  Python-эмулятор остановлен: C#-сторона просто перестаёт получать байты,
  порт остаётся открытым и не бросает исключение. Реалистичный тест
  потребовал бы либо реального USB-serial адаптера (физически выдернуть
  кабель), либо абстракции над `SerialPort` (`ISerialPortFactory`) ради
  фейка — отдельный рефакторинг, не делал его без явного запроса.
  Проверено вручную не было (нет доступа к железу) — **нужно проверить
  руками** перед тем, как полагаться на эту логику.
* Версии пакетов `Microsoft.Extensions.Logging`/`.Console` (`10.0.0`)
  проставлены по аналогии с `System.IO.Ports`, не проверены через NuGet
  (сети не было) — проверить при первом `dotnet restore`.
