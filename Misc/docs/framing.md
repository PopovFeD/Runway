# Framing

Слой между Transport и Protocol. Задача — превратить непрерывный поток байт
(который может прийти рваным, кусками, вперемешку с мусором) в последовательность
целых, проверенных по CRC кадров (`Frame`). Ничего не знает о смысле payload —
это уже зона `Protocol`.

Файлы: `Runway/Core/Framing/Frame.cs`, `FrameHeader.cs`, `FrameReader.cs`.

---

## Зона ответственности

* найти границы кадра в потоке байт (по сигнатуре Magic);
* дождаться, пока кадр придёт целиком (заголовок + payload + CRC);
* проверить CRC-16 и отбросить кадр, если она не совпала;
* вернуть готовые `Frame`, не трогая то, что внутри payload.

Explicitly **не** входит в зону ответственности: интерпретация `MessageType`,
разбор содержимого payload (temperature/humidity и т.п.) — этим занимается
`Protocol.PacketParser`.

---

## Формат кадра на проводе

```text
[Magic 2 байта][Version 1][MessageType 1][Sequence 2][PayloadLength 2][Payload N][CRC16 2]
```

Константы вынесены в `FrameHeader`:

```csharp
public static readonly byte[] Magic = { 0xAA, 0x55 };
public const int HeaderSize = 2 + VersionSize + MessageTypeSize + SequenceSize + PayloadLengthSize; // = 8
```

`Sequence` и `PayloadLength` — little-endian (младший байт первый), это же
предполагает и `mc_emulator.py` на стороне Python (`struct.pack("<...")`).
Единственное исключение — сам `Magic`: это два байта фиксированного значения
`AA 55`, а не число, упакованное как little-endian `0xAA55` (иначе получилось
бы `55 AA` — реальный баг, найденный и исправленный на этапе первого e2e,
см. `Misc/diary/2026.07.08.md`).

`Frame` (результат разбора) — простой value-holder без логики:

```csharp
public class Frame
{
    public byte Version { get; }
    public byte MessageType { get; }
    public ushort Sequence { get; }
    public byte[] Payload { get; }
}
```

## `FrameReader` — как это работает

Стейтфул: накапливает недополученные байты в `_buffer` между вызовами `Append`.
Один вызов `Append(byte[] newBytes)` может вернуть 0, 1 или несколько кадров сразу
(если за один `Read()` транспорта пришло сразу несколько кадров подряд).

Алгоритм `TryExtractOneFrame` на каждой итерации:

1. ищет позицию Magic в буфере (`FindMagic`);
2. если Magic не найдена вообще — весь буфер считается мусором и очищается целиком;
3. если Magic найдена не в начале — байты перед ней (мусор) выбрасываются;
4. если буфера не хватает даже на заголовок — ждём (`return null`, буфер не трогаем);
5. как только заголовок есть — читаем `PayloadLength` и считаем полный ожидаемый
   размер кадра; если данных всё ещё не хватает — снова ждём;
6. когда кадр целиком в буфере — считаем CRC-16 по всему кадру кроме самой CRC
   и сравниваем с полученной;
7. **если CRC не совпала** — это не настоящий кадр, а случайное совпадение байт
   с сигнатурой Magic внутри мусора/предыдущих данных. В этом случае убирается
   **только первый байт** (не весь предполагаемый кадр), и поиск Magic начинается
   заново со следующей позиции. Это важно: агрессивное отбрасывание всего блока
   при неверной CRC могло бы съесть начало следующего настоящего кадра, если
   Magic-подобные байты случайно оказались внутри чужого payload.

Цикл в `Append` вызывает `TryExtractOneFrame`, пока та не вернёт `null` —
то есть готовые кадры извлекаются жадно, все сразу за один `Append`.

## Известные компромиссы

* **`List<byte>` как буфер.** `_buffer.RemoveRange(0, n)` — операция O(размер
  оставшихся данных), поскольку `List<T>` сдвигает все элементы после удаления
  из начала. При низком трафике (единицы кадров в секунду, как в текущем
  эмуляторе) это не проблема. Если поток данных станет высокочастотным —
  стоит рассмотреть `RingBuffer`/`ArraySegment`-подход вместо `List<byte>`.
* **Нет верхнего предела на размер мусора до Magic.** Если Magic вообще не
  встретится очень долго (например, устройство шлёт что-то не по протоколу),
  `_buffer` в теории может накапливаться, прежде чем целиком очиститься на шаге 2.
  На практике при первом же байте, не совпавшем с `Magic[0]`, буфер чистится
  целиком, так что риск скорее теоретический, но стоит держать в уме, если
  протокол расширится и появится, например, потоковая передача не-кадровых данных.

## Тестирование

Юнит-тесты — `Runway.Tests/UnitTest1.cs` (класс `FrameAndCrcTests`):
целиком-и-разом собранный кадр, кадр по частям (`Append` вызывается дважды —
проверяет накопление в `_buffer` между вызовами), плюс отдельно `Crc16.Compute`
на эталонных значениях (`"123456789"` → `0x4B37`, пустой payload → `0xFFFF`,
стандартные тест-вектора для CRC-16/MODBUS).

Синтетический билдер кадров для тестов — `Runway.Tests/Support/FrameTestHelper.cs`,
использует те же константы `FrameHeader.Magic`, что и сам `FrameReader` — из-за
этого самосогласованные юнит-тесты **не могли поймать** несовпадение формата
с реальным Python-эмулятором (см. `transport.md`, раздел про баги первого e2e).
Реальную сборку кадра из настоящего потока байт проверяют интеграционные тесты
в `SerialTransportIntegrationTests.cs` (см. `transport.md`).

## Связь с другими модулями

* **Transport** — источник сырых байт (`DataReceived` → `FrameReader.Append`).
* **Protocol** — потребитель готовых `Frame` (`PacketParser.Parse(frame)`),
  дальше уже интерпретирует `MessageType` и `Payload`.
* **ViewModels** — на сегодня единственное место, где `FrameReader` реально
  используется в приложении (`MainWindowViewModel.OnDataReceived`).
